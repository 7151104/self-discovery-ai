# Развёртывание

Конфигурация машины, на которой живёт сервис: служба, расписание копий, выпуск и
откат. Ничего специфичного для конкретной площадки здесь нет — нужна машина с
systemd и Node. Площадка и домен ждут ответа основателя (открытые вопросы 4 и 29
в `docs/14-state.md`), поэтому конкретных адресов в файлах нет и заглушек с
выдуманным доменом тоже.

Команды разработчика (сборка, проверки, копии вручную) — в `SETUP.md`.

## Что в каталоге

| Файл | Что делает |
|------|------------|
| `sdai.service` | Служба: запускает сервер, читает переменные из файла окружения |
| `sdai-backup.service` | Копия базы и удаление копий старше срока |
| `sdai-backup.timer` | Расписание копий: раз в сутки |
| `release.sh` | Выпуск: проверка миграций, копия базы, применение миграций, переключение |
| `rollback.sh` | Откат на предыдущий выпуск одной командой |

## Раскладка на машине

```
/srv/sdai/releases/<версия>   выпуски: собранное дерево репозитория
/srv/sdai/current             ссылка на текущий выпуск, её читает служба
/srv/sdai/previous            имя предыдущего выпуска, из него берёт откат
/etc/sdai/production.env      переменные окружения, права 0600
/var/lib/sdai/app.db          база
/var/backups/sdai/            резервные копии
```

База и копии лежат **вне** каталога выпуска. Это не вкус: выпуск заменяется и
удаляется по сроку хранения, и данные внутри него исчезли бы вместе с ним.
Поэтому `SDAI_DB_PATH` и `SDAI_BACKUP_DIR` обязательны в рабочем и
предварительном окружениях — путь по умолчанию лежит внутри дерева репозитория.

## Два окружения

Рабочее и предварительное — две службы на одной машине или на двух, с
**раздельными** файлом базы, ключом шифрования и каталогом копий:

| | рабочее | предварительное |
|---|---|---|
| `SDAI_ENV` | `production` | `staging` |
| служба | `sdai.service` | тот же файл как `sdai-staging.service` |
| окружение | `/etc/sdai/production.env` | `/etc/sdai/staging.env` |
| база | `/var/lib/sdai/app.db` | `/var/lib/sdai/staging.db` |
| копии | `/var/backups/sdai/` | `/var/backups/sdai-staging/` |
| платежи | реальный провайдер | поддельный (`fake`) |

Поддельный провайдер и `SDAI_ENV=production` несовместимы: с таким сочетанием
сервер не стартует (E8-09). В предварительном окружении он разрешён — платный
путь там проходится без денег.

Ключи шифрования у окружений разные, и это единственное, что по-настоящему
разделяет данные: копия предварительного окружения рабочим ключом не читается и
наоборот. Отдельный ключ на окружение — не удобство, а граница.

## Установка

```
useradd --system --home /srv/sdai sdai
mkdir -p /srv/sdai/releases /etc/sdai /var/lib/sdai /var/backups/sdai
chown -R sdai:sdai /srv/sdai /var/lib/sdai /var/backups/sdai

# Переменные: состав — .env.example в корне репозитория.
install -m 0600 /dev/null /etc/sdai/production.env
# ключ шифрования печатает `npm run keygen`, в репозиторий он не попадает

cp deploy/sdai.service deploy/sdai-backup.service deploy/sdai-backup.timer /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now sdai.service sdai-backup.timer
```

## Выпуск

```
deploy/release.sh <каталог-сборки> <версия>
```

Каталог сборки — дерево репозитория после `npm ci && npm run build`. Версия —
любая устойчивая строка; она попадает в ответ `GET /api/health`, поэтому по
ответу видно, что развёрнуто.

Порядок шагов жёсткий и проверяется тестом `server/src/deploy.test.ts`:

1. проверка миграций нового выпуска (`migrate check`);
2. резервная копия базы;
3. применение миграций (`migrate up`);
4. переключение ссылки `current`;
5. перезапуск службы;
6. удаление выпусков старше последних `SDAI_KEEP_RELEASES` (по умолчанию 5).

Несовместимая миграция останавливает выпуск **до** переключения ссылки: служба
продолжает работать на прежней версии.

## Откат

```
deploy/rollback.sh
```

Переключает `current` на предыдущий выпуск и перезапускает службу. Версия сборки
в `/api/health` меняется вместе со ссылкой: она лежит в `release.env` внутри
самого выпуска.

Схему базы откат не трогает — намеренно. Откат кода данных не теряет, откат
схемы теряет, поэтому он делается отдельной осознанной командой:

```
node /srv/sdai/current/server/dist/db/migrate.js down --steps=<сколько>
```

Копия базы до выпуска уже снята: её снял `release.sh` третьим шагом.

## Чего здесь ещё нет

Автоматического деплоя из основной ветки: он требует доступа к площадке, а
площадка не выбрана (открытый вопрос 29). Когда она появится, добавится
`.github/workflows/deploy.yml`, который делает ровно то же, что `release.sh`,
через доступ из секретов репозитория; сами скрипты не изменятся.

Внешней проверки доступности (E10-09) и трекинга ошибок (E10-06) — по той же
причине: обе смотрят на работающий адрес.
