# Серверная часть

Транспорт и хранение личной страницы. Правил продукта здесь нет: скоринг,
узлы, блоки, карту и предложения считает движок в `engine/`, тексты живут в
`content/*.md`. Сервер вызывает движок и складывает результат в базу.

Как поднять локально — `SETUP.md` в корне. Решения по стеку и базе с
обоснованием — `docs/14-state.md`, раздел «Принятые решения».

## Состав

| Каталог | Что внутри |
|---------|------------|
| `src/contract/` | Контракт API: типы запросов и ответов, реестр эндпоинтов. Клиент собирается из него же |
| `src/db/` | Порт базы, реализация на `node:sqlite`, миграции, шифрование чувствительных полей |
| `src/http/` | Маршрутизатор из реестра контракта, обработчики, лимиты частоты, проверка ответа на выходе, оболочки адресов `/p/{profileId}` и `/s/{token}` |
| `src/payments/` | Порт платёжного провайдера, поддельная реализация, реестр, таблица переходов заказа |
| `src/store.ts` | Единственный модуль, который знает SQL |
| `src/page.ts` | Проекция результата движка в контракт |
| `src/log.ts` | Журнал с чисткой персональных данных на входе |
| `migrations/` | Пары `NNNN_имя.up.sql` и `NNNN_имя.down.sql` |

## Эндпоинты

Полное описание с типами — `src/contract/api.ts`. Читать его достаточно, чтобы
написать клиент.

| Операция | Метод и адрес | Зачем |
|----------|---------------|-------|
| `health` | `GET /api/health` | Здоровье сервиса и номер применённой миграции |
| `createProfile` | `POST /api/profiles` | Ступень 0: профиль и постоянная ссылка |
| `pageState` | `GET /api/p/:profileId` | Состояние страницы целиком |
| `submitPortion` | `POST /api/p/:profileId/portions` | Отправка порции ответов |
| `editAnswer` | `PATCH /api/p/:profileId/answers/:questionId` | Правка одного ответа |
| `disagree` | `POST /api/p/:profileId/disagreements` | Несогласие с блоком |
| `purchase` | `POST /api/p/:profileId/orders` | Покупка среза: заказ и адрес оплаты |
| `refund` | `POST /api/p/:profileId/orders/:orderId/refunds` | Возврат средств и отзыв доступа |
| `webhook` | `POST /api/payments/:provider/webhook` | Уведомление провайдера: единственный вход к оплаченному заказу |
| `blockText` | `GET /api/p/:profileId/blocks/:slot` | Текст блока; платный требует оплаченного заказа |
| `generationStatus` | `GET /api/p/:profileId/generations/:generationId` | Статус генерации текста |
| `exportProfile` | `GET /api/p/:profileId/export` | Выгрузка данных человека |
| `deleteProfile` | `DELETE /api/p/:profileId` | Удаление профиля со всем содержимым |
| `share` | `POST /api/p/:profileId/share` | «Поделиться»: включить публичную ссылку |
| `revokeShare` | `DELETE /api/p/:profileId/share` | Отозвать публичную ссылку |
| `publicPage` | `GET /api/s/:token` | Публичный вид по токену |

Плюс адреса самих страниц: `GET /p/:profileId` и `GET /s/:token`.

Отказы отвечают машинным кодом (`ErrorCode`), без текста для человека: текст
берётся из контента на стороне клиента.

## Координаты наружу не уходят

Требование из `docs/14-state.md` закреплено типами, а не договорённостью.
`src/contract/wire.ts` объявляет список полей внутреннего профиля — `value`,
`band`, `confidence`, `code`, `flags`, `sources`, `coordinate`, `coordinates`,
`nodes`, `dominantNode`, `nextPaidOffer`, `profile`, `internalProfile`,
`llmTask` — и тип `Wire<T>`, который рекурсивно обходит `T`. Если поле из
списка встретилось на любой глубине, `Wire<T>` перестаёт быть формой ответа и
становится `CoordinateLeak<'имя поля'>`: присвоить ему объект нельзя, сборка
падает и называет утёкшее поле.

Все ответы API объявлены как `Wire<...>`, поэтому обойти стену можно только
осознанно — вписав новое поле в контракт и получив ошибку компиляции.

Проверки: `src/contract.test.ts` (строки с `@ts-expect-error` требуют, чтобы
протёкший тип не собирался, и ломаются, если стену ослабить) и прогон всех
семи состояний `s0`–`paid_done` через API с проверкой ключей ответа.

Вторая линия — `src/http/guard.ts`: перед отправкой ответ обходится и падает,
если встретилось запрещённое поле. Она нужна на случай формы, собранной в обход
типов — приведением или объектом из базы.

## Блоки 3 и 4 не отдаются постороннему

Тот же приём, второй стеной. `src/contract/wire.ts` объявляет `PrivateSlot`
(`step3`, `step4`, `slice:*`) и тип `Viewable<T>`: форма, в которой поле
способно принести закрытое место блока, перестаёт быть присваиваемой.

Публичный вид описан отдельным типом `PublicPageDto`, у блока в нём место
сужено до `"step1" | "step2"`. Спрятать блок фильтром на выходе, оставив общий
тип `BlockDto`, не получится — общий тип не соберётся.

Фраза-крючок при этом публична: по `docs/11-ui-page-spec.md` скриншотятся
именно крючок и карта. Крючок совпадает с первым предложением блока 3 — это
замысел, а не протечка: граница проходит по блокам, и разбор за крючком в
публичный вид не уходит.

## Приватность и лимиты

Страница закрыта, пока человек не нажал «Поделиться»: до этого строки в
`share_tokens` нет, и любая публичная ссылка отвечает `404`. Отзыв помечает
токен и выданный адрес умирает навсегда; новое «Поделиться» выдаёт другой.

Лимиты частоты — скользящее окно в памяти процесса, четыре корзины: создание
профилей, порции, запросы состояния и промахи (перебор идентификаторов).
Пределы задаются переменными `SDAI_RATE_*`, состав — в `.env.example`.

## Оплата

Маршрут оплаты написан против порта `src/payments/provider.ts`. В репозитории
живёт поддельный провайдер: он проходит весь путь без денег и подписывает
уведомления так же, как настоящий — HMAC-SHA256 по телу запроса. Реальный
адаптер добавляется модулем рядом и строкой в `src/payments/registry.ts`.

Оплаченным заказ становится только уведомлением провайдера: у клиента такого
перехода нет. Порядок обработки — подпись, защита от повторной доставки, заказ.
Три доставки одного уведомления выдают доступ один раз.

Оплата открывает вопросы, а не отчёт (Закон 2). Пока у оплаченного среза
остались неотвеченные вопросы, блока среза не существует вовсе; он заводится,
когда добор пройден целиком, и ждёт текста от LLM (E4).

Тестовый режим и рабочее окружение несовместимы: `SDAI_ENV=production` вместе с
поддельным провайдером не даёт серверу стартовать. Ручной прогон платного пути —
`npm run pay -- <адрес> <заказ> <платёж> <сумма>`.

## Шифрование при хранении

Имя, дата рождения, ответы, снимки профиля, заголовки и тела блоков шифруются
AES-256-GCM. Ключ — `SDAI_ENCRYPTION_KEY`, 32 байта в base64; новый печатает
`npm run keygen`. В рабочем окружении переменная обязательна; в разработке без
неё записи остаются открытыми, и сервер говорит об этом строкой
`encryption.disabled`.

Смена ключа не требует простоя: новый ключ в `SDAI_ENCRYPTION_KEY`, старый в
`SDAI_ENCRYPTION_KEYS_RETIRED`. Новые записи пишутся новым, старые ещё читаются
старым; `npm run reencrypt` переписывает остаток, `npm run reencrypt -- status`
показывает, сколько записей чем зашифровано. После этого старый ключ убирается.

## Журналы

`src/log.ts` чистит записи на входе: значения запрещённых полей и всё, что не
похоже на машинный код, заменяются пометкой. Таблица `events` проходит ту же
чистку — это такой же журнал, только в базе.

## Чего тут нет

Генерация текстов (E4) и подключение реального платёжного провайдера (E8-01a).
